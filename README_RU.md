# Meal Generator

AI-ассистент для планирования питания. Пользователь описывает, чего хочет,
на естественном языке — "3 приёма пищи, ~2000 ккал, много белка, без
молочки, что-то в азиатском духе" — а система превращает это в структурные
ограничения, находит подходящие рецепты в курированном корпусе из более чем
300 тысяч реальных рецептов и жадно собирает три разных варианта дневного
рациона, каждый с объяснением на понятном языке. Дальше план можно уточнять
в диалоге, по одному блюду за раз ("замени обед на что-нибудь без грибов").

## Архитектура

```
сырые данные Food.com (522k рецептов)
  → preprocessing (техническая валидация, нормализация КБЖУ на порцию,
     мульти-лейбл классификация типа приёма пищи, извлечение
     allergen-категорий, отсев неправдоподобных значений)
  → sentence-transformer эмбеддинги → Qdrant (dense-векторы + payload-фильтры)
  → LangGraph-агент (OpenAI structured outputs: классификация intent →
     парсинг запроса → retrieval кандидатов → сборка 3 вариантов плана →
     объяснение; диалоговое уточнение отдельных блюд)
  → FastAPI-бэкенд (держит LLM-клиент, embedding-модель, Qdrant-клиент и
     скомпилированный граф)
  → Streamlit чат-клиент (тонкий HTTP-слой, без собственных ML-зависимостей)
```

Пайплайн лежит в `src/meal_generator/`:

- `preprocessing/` — превращает сырые строки Food.com во внутреннюю схему
  (`recipes.py`), классифицирует тип приёма пищи (`meal_types.py`) и
  allergen-категории (`exclusions.py`), строит текст для эмбеддинга
  (`embedding_text.py`).
- `indexing/` — строит payload для Qdrant и апсертит курированный корпус
  (`qdrant_index.py`).
- `retrieval/` — комбинирует семантический поиск со структурными
  payload-фильтрами (`search.py`).
- `planning/` — собирает дневной план из полученных кандидатов жадными
  эвристиками (`optimizer.py`).
- `nlp/` — парсит свободный текст пользователя в структурные запросы и
  уточнения через OpenAI structured outputs (`parse_request.py`,
  `parse_refinement.py`).
- `graph/` — связывает всё это в LangGraph-граф состояний (`graph.py`,
  `nodes.py`, `state.py`).
- `api/` — FastAPI-приложение, владеющее всеми тяжёлыми ресурсами процесса
  (`server.py`, а также схемы запросов/ответов и сериализация).

## Ключевые инженерные решения

- **Мульти-лейбл классификация типа приёма пищи вместо single-label с
  приоритетом.** Рецепт вполне может одновременно быть и `main_meal`, и
  `lunch_snack`; принудительный выбор одного лейбла с приоритетом молча
  отбрасывал бы валидные совпадения. `classify_meal_types` возвращает все
  типы, для которых нашёлся хотя бы один сигнал, а не одного "победителя".

- **Token-based матчинг для exclusion-фильтрации аллергенов, точное
  совпадение — для классификации типа приёма пищи: разные задачи, разный
  матчинг.** Сигналы для типа приёма пищи берутся из структурированных
  полей Food.com (`source_category`, `keywords`), поэтому точное сравнение
  нормализованных строк корректно. Текст ингредиентов — произвольные фразы
  ("almond flour", "2 cups milk"), поэтому exclusion-фильтрация токенизирует
  каждый ингредиент и матчит по отдельным словам. Trade-off явно
  задокументирован в коде: токен "flour" матчит `gluten_wheat` даже в
  "almond flour" — осознанное, принятое упрощение v1, а не баг.

- **Нормализация КБЖУ на порцию.** Поля `Calories`/`ProteinContent` и
  остальные в Food.com — это значения на весь рецепт целиком (все
  `RecipeServings` порций), а не на одну порцию — факт, который молча ломал
  все нижестоящие фильтры по калориям, таргеты оптимизатора и цифры,
  показываемые пользователю, пока не был найден и исправлен. Теперь
  `build_curated_recipes` делит на `servings` один раз, на шаге
  преобразования схемы, так что весь остальной код может считать
  `calories`/`protein`/`fat`/`carbs` значениями на одну порцию.

- **Жадные эвристики вместо ILP-солвера для сборки дневного плана.** Три
  варианта (balanced / quick_cooking / variety) строятся простым жадным
  проходом по слотам — выбор локально лучшего кандидата под текущий
  остаточный таргет по калориям. Это осознанный MVP trade-off: на порядки
  проще реализовать, отладить и объяснить пользователю, чем формулировать
  задачу как глобальную ILP-оптимизацию (OR-Tools/PuLP) сразу по
  калориям/времени/разнообразию. Апгрейд до солвера — будущий шаг, если
  жадный подход на практике даст заметно неоптимальные планы.

- **sentence-transformers/MiniLM вместо OpenAI-эмбеддингов.** Эмбеддинги
  рецептов считаются локально моделью `all-MiniLM-L6-v2`, а не через
  OpenAI embedding endpoint — корпус остаётся self-contained, и индексация
  не создаёт рантайм-зависимости от внешнего API и не добавляет
  latency/cost на шаг, который в принципе нужно выполнять раз на весь
  ребилд корпуса.

- **Разделение семантического и rating-based retrieval (query bleed
  problem).** Эмбеддинг пустого `query_text` даёт вырожденный вектор,
  косинусное сходство с которым — фактически шум, замаскированный под
  осмысленный score. Хуже того, vibe-запрос вроде "spicy asian dinner"
  семантически "перетягивал" завтрак к несвойственным ему, ужиноподобным
  результатам. `search_recipes_by_rating` — второй, non-semantic путь
  retrieval (структурные фильтры + сортировка по рейтингу/числу отзывов),
  используемый, когда `query_text` пуст, и всегда — для слотов завтрака,
  независимо от содержимого запроса, как осознанный point-fix для этой
  проблемы.

- **FastAPI + Streamlit как два отдельных процесса.** Бэкенд владеет всеми
  тяжёлыми, медленно инициализирующимися ресурсами (LLM-клиент,
  embedding-модель, Qdrant-клиент, скомпилированный LangGraph-граф) через
  `@lru_cache`-геттеры, собираемые один раз за жизнь процесса. Streamlit-клиент
  общается с ним только по HTTP. Это избавляет от cold start ML-библиотек
  на каждый rerun Streamlit и следует тому же паттерну разделения
  процессов, что уже применялся в других проектах с тяжёлыми
  ML-зависимостями.

## Стек

Python · pandas/numpy · sentence-transformers · Qdrant · LangGraph ·
OpenAI API (structured outputs) · FastAPI · Streamlit · Docker · unittest

## Данные

Рецепты взяты из датасета [Food.com Recipes and Reviews на
Kaggle](https://www.kaggle.com/datasets/irkaal/foodcom-recipes-and-reviews)
(~522k рецептов). `data/recipes.parquet` и `data/reviews.parquet` **не
включены в этот репозиторий** — они превышают лимит GitHub на размер файла.
Скачайте датасет с Kaggle и положите оба parquet-файла в `data/` перед
запуском индексации ниже.

## Установка и запуск

1. Склонируйте репозиторий и установите зависимости:

   ```
   pip install -e .
   ```

2. Скопируйте `.env.example` в `.env` и заполните OpenAI API key:

   ```
   cp .env.example .env
   ```

3. Скачайте датасет Food.com с Kaggle (см. [Данные](#данные)) и положите
   `recipes.parquet`/`reviews.parquet` в `data/`.

4. Запустите Qdrant локально:

   ```
   docker-compose up -d
   ```

   UI дашборда: http://localhost:6333/dashboard

5. Постройте индекс — разовая операция, которая загружает embedding-модель,
   фильтрует и классифицирует весь датасет и индексирует его в Qdrant.
   Занимает примерно 20-40 минут для полного датасета:

   ```
   python scripts/build_index.py
   ```

6. Запустите приложение как два процесса. В одном терминале — FastAPI-бэкенд:

   ```
   python -m uvicorn meal_generator.api.server:app --reload
   ```

   В другом — Streamlit-клиент:

   ```
   streamlit run app.py
   ```

   По умолчанию клиент обращается к `http://127.0.0.1:8000`; чтобы указать
   другой адрес, задай `API_URL` в `.env`.

## Тесты

```
python -m unittest discover -s tests -v
```

214 тестов по всему пайплайну. Тесты используют in-memory Qdrant-клиент
(`QdrantClient(":memory:")`) и фейковые LLM-клиенты — реальный
Qdrant-контейнер, embedding-модель или OpenAI API key для запуска
тестового набора не нужны.
